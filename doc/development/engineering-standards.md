# 编码、数据与接口规范

## 编码与分层

- 沿用若依现有分层、Java 排版、Mapper XML 和 Vue 组件习惯；先阅读相邻功能再编码。
- Controller 负责请求适配、校验和权限声明，Service 承载业务规则与事务，Mapper 负责持久化；前端负责交互，不能作为业务约束的唯一执行处。
- 优先复用现有权限、日志、分页、异常处理和前端请求封装。代码生成结果必须复核权限、校验、状态、事务和数据访问范围。
- ERP 页面及后续细节调整持续参考领星对应 UI 和实际交互，实施前查看、实施后核对；测试账号录入授权、验证方式和记录要求遵循[开发计划](development-plan.md)的 UI 与交互执行约定。
- 不为简单功能创建无实际用途的通用层；复杂业务按职责拆分，避免一个 Service 混合多个完整业务域。

## 数据建模

- 表和列沿用现有小写下划线习惯，Java 字段使用驼峰。新业务表采用清晰且一致的业务前缀，不混入若依系统表命名空间。
- 同模块主键类型与生成方式保持一致，新业务默认沿用现有自增 BIGINT 风格；外部平台标识使用适合其格式的字符串字段，独立建立唯一约束。
- 审计字段沿用 `create_by`、`create_time`、`update_by`、`update_time` 等实际约定；关键业务补充操作原因和业务时间。客户端不得任意覆盖服务端审计值。
- 按实际范围设计 DECIMAL 精度和小数位，设计表时同时说明金额、单价、汇率和数量的取值上限、单位、舍入方式及分摊尾差处理；不直接给所有金额套同一小数位。
- 原币、原币金额、汇率日期、适用汇率及本币金额明确记录；未确定值与合法零值区分。
- 关联关系、必填字段、唯一键及检查约束在表设计中明确；是否使用物理外键结合现有数据库和删除策略说明，不以缺少外键为由省略一致性校验。
- 基础资料优先停用；受历史单据引用的资料保留。逻辑删除需明确唯一约束及查询行为，不能统一套到所有流水表。
- 索引围绕真实查询、排序和关联设计；列表排序具有稳定的次级排序键。重要写操作评估并发和受影响行数。
- 时间存储与接口序列化遵循根目录约定；新增时间方案须兼容既有 `BaseEntity` 和前端格式，不无差别替换框架时间字段。

## 接口契约

- 请求分页默认每页 10 条，最多 100 条；非正页号归为 1，非正或无法解析的条数归为 10，超出上限截为 100。通过现有 PageUtils 入口实施；导出及绕过该入口的查询另按其任务验证。
- 分页接口使用 `startPage(defaultOrderBy, uniqueOrderBy)`，默认排序及唯一键由服务端定义，客户端指定排序后仍追加唯一键。不得让客户端提供唯一键 SQL；保持既有默认业务排序，补齐同值记录的次级排序。现有 16 个分页入口已接入；新增业务列表遵循此入口。同一数据集下排序稳定不代表并发增删时 offset 分页具有快照一致性。

- 普通响应沿用 `AjaxResult` 的 `code`、`msg`、`data`，分页沿用 `TableDataInfo` 的 `rows`、`total` 等现有字段及 PageHelper 习惯；不另造一套统一响应。
- 明确接口参数、默认值、分页上限、状态前置条件、返回字段、金额单位和时间口径。接口修改同步调用端与相关文档。
- 使用项目现有校验机制；业务失败经现有异常处理输出可理解信息，不能返回空成功、泄露堆栈或把失败当作无记录。
- 沿用既有状态码规则；需要细分业务错误时集中定义且保持兼容，不临时改变前端拦截器对 `code` 的解释。
- 权限标识沿用 `模块:资源:操作` 风格并配置菜单或角色关系。查询、导出和修改均检查后端权限及适用数据范围。
- 读取接口不产生库存或资金效果。关键写操作明确幂等键或唯一业务依据；前端按钮禁用和请求防抖不能替代后端幂等。
- 并发修改采用版本或条件更新等适当方式；冲突提示刷新或重新核对，不静默覆盖已变化数据。
- 外部同步保留来源身份和更新时间，分页、限流和失败续处理有边界；外部字段到内部字段的映射显式管理。

## Git 与环境

- 默认新分支使用 `codex/` 前缀，用户指定时以用户要求为准。不擅自提交、推送、合并或发布。
- 2026-10-11 起，功能开发、缺陷修复和独立工程维护均先创建对应主题分支，不直接在 `master` 开发。命名采用 `codex/feat-<主题>`、`codex/fix-<主题>`、`codex/chore-<主题>`；一个分支围绕一个可审查主题，可以包含该功能关联的迁移、接口、页面、测试及文档。
- 建分支前核对工作区、当前提交及远端基线；保留他人未提交修改，不擅自重置、覆盖或强推。通常从已同步的 `master` 创建；继续已有功能时复用对应分支，依赖尚未合并的功能时明确记录基线和依赖。
- 分支关联任务台账 ID，开始及交付时在执行记录中登记分支、基线、范围和验证证据。提交信息引用任务 ID；合并前审查最终差异、业务规则、权限、迁移兼容/恢复和实际测试结果，优先通过 PR 保留评审记录。
- 创建本地功能分支不包含提交、推送、创建 PR、合并或部署授权。继续遵守当前不触发 GitHub Actions 的约束，使用本地验证；未运行 CI 如实记录，不为功能分支新增工作流或解除现有限制。
- 提交围绕一个主题，建议 `feat:`、`fix:`、`docs:`、`refactor:`、`test:`、`chore:` 加简洁说明；发布版本使用可追溯标签，关联变更和数据库升级说明。
- 合并前审查业务行为、兼容性、权限、数据库影响和必要验证。不得覆盖他人工作或提交临时材料。
- 开发、测试、生产配置隔离，提供不包含真实密钥的配置样例。真实授权、连接串和凭据由环境注入或安全配置提供。
- 测试使用独立数据库和模拟外部服务；对真实 Amazon 账户的写操作必须有明确业务授权，不能以测试为由执行。
- 构建命令、运行前提维护在模块 README；不能将未经验证的环境或构建步骤描述为可用。
