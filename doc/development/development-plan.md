## 2. ERP 模块如何组织和执行

沿用模块化单体，`erp-business` Maven 模块已接入，集中承载 ERP 领域对象、Service、Mapper 和外部平台适配；`ruoyi-admin` 依赖它。模块依赖 `ruoyi-common`，按实际需要使用已有系统服务，不反向依赖 Web 入口模块。业务按包划分，不为每个业务域建立独立服务或独立部署。

| 业务包建议 | 职责 |
|---|---|
| `catalog`、`supplier` | 商品、图片版本、供应商报价、规格、配方版本、Listing 配对 |
| `demand`、`purchase`、`logistics` | 提需、分配、供应商拆单、采购及国内运输 |
| `inventory`、`production` | 批次、库存流水、占用、FIFO 投料、加工与成品成本 |
| `fba`、`sales` | 发货、接收差异、销售、退款及实物退货 |
| `finance`、`cash` | 汇率快照、费用归集、成本调整、利润和收付款 |
| `replenishment`、`advertising` | 补货建议、待办、广告导入与分析 |
| `integration.amazon` | LWA、SP-API 调用、外部数据映射、同步任务与恢复 |

前端新增 `src/api/erp/`、`src/views/erp/`，按上述业务拆目录。业务表采用 `erp_` 前缀，菜单与操作权限同步迁移。保留 `AjaxResult`、`TableDataInfo` 和现有异常处理，不新增一套 API 协议。具体包名、表结构及精度在对应任务设计时落地。

每次开发交付一个可操作的业务场景，包含数据库、后端、页面、权限、测试及文档，避免先堆完全部表和 CRUD 再补事务。普通资料维护可使用代码生成器起草；收货、占用、完工、发货、成本结转等业务命令必须单独设计。

核心执行要求：

1. 提需提交可执行，采购确认即可下单，不增加审核流程。所有单据明确草稿、确认、部分执行、完成、取消及允许修改字段。
2. Service 事务内完成状态校验、数量校验、来源记录和库存/费用流水，数据库唯一约束及条件更新或锁保证并发正确性。
3. 占用、收货、完工、发货、销售结转分别使用明确业务依据防重复。现有前端请求防抖及 RepeatSubmit 只作为交互保护。
4. 业务日期、来源时间点、原币、适用汇率、配方和图片版本按确认事实保存。已完成记录通过关联调整纠错。
5. 外部网络调用不放在持有库存锁的长事务内。先获取、暂存外部数据，再用短事务处理；异常留待办，不直接改库存余额。
6. 每个模块落实后端操作权限和适用数据范围；若依部门数据范围不直接等同于 ERP 单据访问规则，实施前定义访问矩阵。

## 4. SP-API 对接方案

### 4.1 授权与客户端

现有单店、自有应用场景建议使用私有卖家应用自授权，先核对已有应用类型与角色，不重新搭建面向第三方商户的公开 OAuth 平台。[Amazon 私有应用授权文档](https://developer-docs.amazon.com/sp-api/docs/self-authorization)说明自授权生成 refresh token，运行时经 LWA 换取 access token。

后端安全配置注入 LWA client ID、client secret、refresh token，店铺保存 seller ID、区域、Marketplace ID、启用日期及业务时区。密钥不通过聊天、前端、普通系统参数明文或日志传递；如后续提供在线维护，必须加密保存、限制访问并支持撤销轮换。access token 按有效期缓存，刷新采用并发互斥。

[Amazon 已取消 SP-API 的 IAM/SigV4 必需条件](https://developer-docs.amazon/sp-api/lang-fr_FR/changelog/sp-api-will-no-longer-require-aws-iam-or-aws-signature-version-4)，本项目不因旧教程额外建设 AWS 签名链路。Java 客户端优先评估 Amazon 官方 SDK 对目标接口和 Java 17 的覆盖，再决定固定版本；仅当缺失必要接口时按官方模型补适配。依赖选择须记录兼容性、许可证及维护成本，当前计划不承诺某 SDK 版本已验证可用。

### 4.2 数据来源与接入顺序

Java SDK 选型已核实：Amazon 提供维护中的预构建 Java SDK，Maven 坐标为 `software.amazon.spapi:spapi-sdk`，官方要求 Java 11 及以上；源码使用 Apache-2.0 许可证。参见[官方 Java 接入教程](https://developer-docs.amazon.com/sp-api/docs/automate-your-sp-api-calls-using-prebuilt-java-sdk)和[官方开源仓库](https://github.com/amzn/selling-partner-api-sdk)。这是 SP-API 专用 SDK；项目按该 SDK 选型，不以通用 AWS 服务 SDK 替代。无需从零编写全部 HTTP 客户端和数据模型。

用户已确认优先采用 Amazon 官方 Java SDK（`software.amazon.spapi:spapi-sdk`），将其作为 SP-API 客户端的默认实现选择。阶段 0 检查目标接口版本覆盖、Java 17 与当前依赖兼容性、超时和限流行为，再固定版本；不直接使用教程的示例版本。官方 SDK 负责接口调用及 LWA 等基础能力，项目负责业务同步调度、游标、幂等、映射、对账、恢复及权限。已有 SDK 能力优先复用，仅补齐实际缺口；第三方开源客户端作为官方 SDK 存在实质缺口时的备选，不提前新增第二套客户端。

当前已固定 SDK 1.13.0，并针对该版本未开放 LWA HTTP 超时注入、默认缓存不能合并并发刷新的缺口增加认证适配；保留官方接口、模型及限流。JDK21/目标17的初轮结果及后续实际Java17干净编译/完整隔离回归、安全配置及未验证项见[接入说明](amazon-sp-api-integration.md)；店铺角色及真实只读连接仍需后续核对。

| 顺序 | 数据 | 拟用来源与内部用途 | 边界 |
|---|---|---|---|
| A | 账号与站点 | Sellers 相关接口核对可访问站点；建立连通性验证 | 不自动扩大当前经营范围 |
| B | Listing、商品规格 | Listings Items / Catalog Items，必要时用指定 Listings 报表补齐发现清单 | MSKU 与内部 SKU 人工确认；平台规格仅作核对，不覆盖已确认实测值 |
| C | FBA 库存 | FBA Inventory 及明确需要的库存/流水报表 | 平台库存快照与 ERP 成本库存分别管理，差异生成核对任务，不直接覆盖成本账 |
| D | 货件及接收 | Fulfillment Inbound 的适用读取接口/报表，按现有货件类型验证覆盖 | Seller Central 创建货件；ERP 关联标识、计划/申报/实发/接收量，不自动提交创建或修改 |
| E | 订单和销售 | Orders API；必要的 FBA 发运/退货报表补齐履约事实 | 不按订单创建即扣库存；履约、取消、退款及实物退货分别处理 |
| F | 平台费用和回款 | Finances API、指定结算报表，按真实返回核对收入、费用、退款和结算 | 订单收入与财务收入对账归并；平台扣款与广告消耗避免重复；结算不等同银行实际到账 |

截至 2026-10-10，[官方 Orders 文档](https://developer-docs.amazon.com/sp-api/docs/orders-api)列出 v2026-01-01 并标明 v0 已弃用，因此新接入以 v2026-01-01 为评估目标，实施时核对角色及 SDK 支持。[Fulfillment Inbound](https://developer-docs.amazon/sp-api/lang-en_us/docs/fulfillment-inbound-api)和[Finances](https://developer-docs.amazon.com/sp-api/docs/finances-api)的具体操作、版本及报表类型在阶段 0 按本店实际授权做接口矩阵，不把全部能力默认视为可访问。

首期仅取经营必需的非敏感字段，不采集买家姓名、地址等不需要的数据。受限字段如确有业务需要，再按具体接口版本的官方规则评估授权，不照搬旧版订单授权机制。广告自动报表走独立广告授权，不视为 SP-API 授权已覆盖。

### 4.3 同步与恢复

调用链：Quartz/人工触发 → 业务同步任务 → LWA/接口客户端 → 外部数据暂存与校验 → 幂等映射 → ERP 业务处理 → 对账及异常待办。

- 为每类任务保存站点、启用边界、请求窗口、分页游标、成功水位、状态、尝试次数和脱敏错误；只在对应数据持久化成功后推进水位。令牌过期时可重启小窗口并幂等去重。
- 首次订单和财务同步限定新业务范围，增量按更新时间或相应 API 支持的时间窗口读取，保留重叠窗口处理延迟和修订。具体窗口和频率根据限额、业务时效和实际数据量配置，不写死统一每分钟全量拉取。
- 按操作控制限流，遵循[官方用量计划](https://developer-docs.amazon.com/sp-api/docs/usage-plans-and-rate-limits)；429、临时网络和服务故障有界退避重试；权限或授权失败进入待处理，不无限重试。记录 Amazon request ID 便于排障。
- Reports 使用创建、查询状态、下载、解析、入库的分阶段任务；下载内容校验大小和格式，临时文件不提交 Git。任务重试不重复发起同一业务导入。
- 外部数据保留身份、来源版本、时区及必要原始字段；不同来源的同一事实建立对应关系。无稳定外部明细 ID 时，经真实样本定义可重复的去重依据，不只按金额去重。
- 未配对 SKU、启用前来源、批次成本缺失、接收差异、重复或修订费用进入可查询待办，不擅自制造期初库存、成本或自动冲销。
- 同步后台展示最近成功时间、覆盖期间、数据量、失败原因和继续处理入口；区分未同步、无记录、失败和资料缺失。

对接验收顺序：模拟响应验证分页/限流/授权过期/重复/修订 → 可用沙箱验证协议 → 用户授权下本店小窗口只读核对 → 增量重跑与中断恢复 → 与 Seller Central 样本对账。沙箱不能替代真实业务对账；当前已授权信息不代表已完成真实 API 验证。

## 5. 实施前需确认的事项

| 事项 | 最迟确认阶段 | 影响及处理 |
|---|---|---|
| 数据库类型/版本、开发测试环境及现有库状态 | 0 | 决定迁移工具和并发测试环境；先检查后选型 |

| 首套真实商品、编码词典、单位换算、供应商及报价 | 1 | 决定 SKU、防重复及配方样例 |
| 库存访问权限、需求目标日期代表国内可用还是 FBA 可售 | 2 | 影响分配权限和排期，未确认前不固化规则 |

| 用户量、数据规模、容量与恢复目标 | 上线前 | 决定性能验收和运维配置，目前未评估 |

## 6. 执行批次与交付管理

按[任务台账](task-board.md)的稳定任务 ID 执行。开始、完成、失败和恢复等事件追加到[执行记录](execution-journal.md)，记录变更文件、验证命令/场景、实际结果、日志路径和未验证项。原始日志按任务 ID 保存在对应环境 `logs/` 或本地 `.local/logs/`，不提交 Git。各阶段内将迁移、业务命令、页面、权限和回归拆为可独立核对任务，发现仍含多个独立成果时继续拆分；每次交付报告本次完成、当前进行、待确认和下一项。

第一批先做阶段 0：验证环境、确定模块依赖、迁移工具决策、首套商品字段设计、SP-API 站点/角色/接口矩阵和只读连通验证。产出可评审的表设计、状态与操作矩阵、接口契约和验证记录，再进入阶段 1 商品与供应商实现。

后续任务按需求编号拆分，每项记录前置条件、输入输出、事务、权限、幂等、异常和验收结果。每阶段交付完整页面路径和可复现样例；关键库存财务功能覆盖正常、边界、重复、并发和失败回滚。参考[需求与验收规范](../requirements/requirements-workflow.md)、[数据库规范](database-migrations.md)及[发布恢复规范](../operations/release-and-recovery.md)。

目前缺少团队投入、真实接口样本和环境验证，不给固定上线日期。阶段 0 完成后按实际任务拆分和可投入人力估算工期，每阶段验收后滚动修订；外部授权等待与开发工作量分别记录。所有阶段均不包含历史迁移、多店、FBM/海外仓、虚拟组合履约、多级审批、完整总账或广告自动投放。
