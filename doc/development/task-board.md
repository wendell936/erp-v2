## 跟进方式

- 以业务为主安排任务：明确任务帮助业务人员完成什么、支撑哪个业务闭环；优先推进已确认且前置就绪的业务成果，必要工程任务关联其业务收益或风险，交付核对实际业务结果。
- 每行是一个可独立评审和验证的任务，保留稳定 ID、需求依据、前置任务、产物或验收条件、状态。默认由 Codex 执行；需要用户资料时明确标记。
- 状态：待开始、执行中、待确认、待验收、已完成、失败、暂缓。暂缓用于用户明确要求仅记录的风险，不表示已修复。待确认只暂停受影响任务；失败记录原因和恢复步骤，修复后重新验证。
- 开始、完成、失败、恢复和范围变化追加到执行记录，关联任务 ID、变更文件、命令/场景、实际结果和未验证项。未经运行的检查不得填通过。
- 原始执行日志保存在 `.local/logs/<任务ID>/`，云端使用对应工作区 `logs/<任务ID>/`，不提交 Git；正式执行摘要和验收结论入库。摘要记录命令、退出码、日志路径和必要校验值，以便关联证据。
- 任务原子性指一个明确成果可独立核对、回退或前向修复；不强求跨数据库、后端、前端的改动能在单个技术事务回滚。迁移、接口、页面、权限和回归分任务，阶段交付仍要求完整业务场景。
- 开始任务前补齐具体输入、输出和用例；发现任务包含多个可独立成果时拆为 `原ID.a`、`原ID.b`，原任务作为汇总项，不重复计数。依赖列省略的通用前置为工程基线和适用业务确认。
- 每次交付报告本次完成、在做、失败/待确认、下一项。以状态和证据跟进，不用任务条数推算工期或业务完成百分比。
- UI 任务均需实施前查看领星对应页面、实施后核对；测试账号可录入 `ERP-TEST-` 数据。不能只验空列表；参考测试结果不等同本项目实现验收。
- 不自动创建 Git 提交。2026-10-11 用户授权提交并推送当前云端修改，供本地接续；提交说明引用任务 ID，实际提交哈希见执行记录。后续新改动的提交/推送另按用户授权执行。
