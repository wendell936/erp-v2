## 审查结论

现有单体模块架构、单公司/单店FBA边界、实体组装与FIFO成本方向可以保留；本轮没有发现需要重新选型或推倒总体方案的依据。已实现范围主要是工程基线、登录/临时解锁、供应商资料、日期汇率和类型/内部编号；完整商品、报价、配方、库存及销售成本闭环仍未实现，台账没有将这些业务标成已完成。

当前实现尚不能直接作为继续录入正式业务的安全基线。本轮确认4项P1、3项P2，其中5项通过真实隔离HTTP/MySQL/Redis复现，2项通过代码/台账静态核对。建议先关闭P1安全和编号问题，再继续商品主线；不需要因此更换框架、增加微服务或引入完整会计系统。审查完成不表示下述缺陷已修复。

## 发现项（按风险排列）

### R01 / P1：账号停用、角色降权及密码重置未使旧会话失效

- 证据：[账号状态/角色入口](../../erp-front/ruoyi-admin/src/main/java/com/ruoyi/web/controller/system/SysUserController.java)、[用户服务](../../erp-front/ruoyi-system/src/main/java/com/ruoyi/system/service/impl/SysUserServiceImpl.java)、[JWT过滤器](../../erp-front/ruoyi-framework/src/main/java/com/ruoyi/framework/security/filter/JwtAuthenticationTokenFilter.java)、[TokenService](../../erp-front/ruoyi-framework/src/main/java/com/ruoyi/framework/web/service/TokenService.java)。状态修改只更新数据库；请求仍信任Redis中的LoginUser和旧角色/权限，并可延长会话。`getInfo`从缓存用户的角色列表计算菜单权限，不能可靠纠正用户角色撤销。
- 实际复现：操作账号先登录；管理员停用成功，数据库status=1，原token仍能列表查询和创建类型（均业务code=200）。恢复启用后，管理员改为只读角色成功，数据库role_id=4，原token仍可创建类型，调用getInfo后仍含`erp:productType:add`。管理员重置密码成功后原token也仍可写入。
- 影响：停用和降权不能切断已有访问，破坏管理员/操作/只读矩阵；有持续请求时不能简单指望30分钟自然过期。原“停用禁止新登录”测试有效，但未覆盖已有会话撤权。
- 建议：在用户停用/删除、角色撤销和密码安全变更时采用一致的会话失效或授权版本校验机制，处理刷新与撤销并发，不能只隐藏前端按钮或依赖用户刷新页面。无需新增授权框架。
- 关闭条件：旧token写入被拒绝，降权只允许读取；重新登录按最新状态/角色生效；覆盖多token、刷新并发及管理员正常操作。修复任务P0-30。

### R02 / P1：通用文件接口绕过只读权限，上传文件可匿名读取

- 证据：[CommonController](../../erp-front/ruoyi-admin/src/main/java/com/ruoyi/web/controller/common/CommonController.java)的`/common/upload`、`/uploads`只有登录要求，无业务写权限声明；[SecurityConfig](../../erp-front/ruoyi-framework/src/main/java/com/ruoyi/framework/config/SecurityConfig.java)放行GET `/profile/**`；[ResourcesConfig](../../erp-front/ruoyi-framework/src/main/java/com/ruoyi/framework/config/ResourcesConfig.java)将整个profile目录映射为静态资源。
- 实际复现：只读账号上传合成`ERP-TEST-audit.txt`得到业务code=200；对返回的文件路径不带Authorization请求，HTTP200且读取到同一测试内容。没有上传或读取真实业务文件。
- 影响：只读账号可以产生文件写入；未来商品附件、供应商文件或导出资料若直接复用该入口，会脱离公司业务身份/权限控制。当前商品图片功能尚未实现，不能把通用上传视作已满足企业ERP附件权限。
- 建议：上传按具体业务写权限校验；私有业务文件用受控读取/下载入口。公开头像与私有业务附件分别明确，不对整个文件根目录匿名放行，不把不可猜URL当权限。
- 关闭条件：只读业务上传403、未登录私有文件读取被拒、合法读取仍符合全公司数据范围；历史图片保护与具体模块引用另验。修复任务P0-31.a/b/c，在商品图片接入前完成。

### R03 / P1：默认MyBatis DEBUG日志可记录密码哈希

- 证据：[application.yml](../../erp-front/ruoyi-admin/src/main/resources/application.yml)默认`com.ruoyi: debug`，仅ERP三组Mapper覆写INFO；系统用户Mapper没有覆写。[SysUserMapper.xml](../../erp-front/ruoyi-system/src/main/resources/mapper/system/SysUserMapper.xml)的resetUserPwd将密码哈希作为绑定参数。
- 实际复现：按仓库默认级别启用用户Mapper DEBUG，在不向控制台传播的内存Appender捕获管理员重置合成密码的日志，`Parameters:`中包含BCrypt哈希，结果`mapper_debug_logs_password_hash=true`。其他配置将系统Mapper降至INFO可减轻此问题，但仓库默认仍不安全。
- 影响：密码派生凭据进入技术日志，扩大离线猜测和日志副本暴露范围。ERP联系方式已关闭Mapper DEBUG与Druid慢SQL原文的措施有效，但不能代表系统账号敏感参数全部保护。
- 建议：默认安全日志级别，密码/密钥/令牌相关SQL禁止输出绑定值，核查相邻异常及审计出口；使用合成敏感标记验证，不在报告记录哈希内容。
- 关闭条件：创建用户、重置/自助改密码及失败分支均不泄漏明文或哈希；保留必要的人员、目标、结果审计。修复任务P0-32。

### R04 / P1：两个已使用类型码可使变体编号持续冲突且无法按现有流程恢复

- 证据：[类型码校验](../../erp-front/erp-business/src/main/java/com/ruoyi/erp/catalog/domain/ProductTypeSaveRequest.java)允许连字符和数字；[编号服务](../../erp-front/erp-business/src/main/java/com/ruoyi/erp/catalog/service/SkuNumberService.java)拼接`类型码-主序号-变体序号`；[类型更新SQL](../../erp-front/erp-business/src/main/resources/mapper/erp/catalog/ProductTypeMapper.xml)禁止已分配主编号的类型改码。SKU全局唯一约束正确拒绝重复，但没有预防这种命名空间重叠。
- 实际复现：创建类型`T`和`T-1`；`T-1`先领主编号`T-1-1`，`T`再领主编号`T-1`，二者都成功且类型码被锁定。`T-1`下面的第一个变体也需要`T-1-1`，连续3次重试均失败；两个已用类型修改类型码均code=500。失败事务回滚正确，但正常增加变体没有当前业务恢复路径。
- 影响：合法输入的类型组合在正式使用后可能阻断新增变体。已有测试覆盖“另一个类型尚未使用时碰撞并改码恢复”，未覆盖“两类型均已使用”的反向顺序。
- 建议：在正式类型录入/使用前明确兼容现有编码格式的命名空间预防策略，例如保留模式或冲突类型约束；不能仅提示原请求无限重试，也不能自行重编号或回收已用SKU。涉及类型码业务限制时先确认，不擅自改变规则。
- 关闭条件：两种录入/使用顺序、大小写、主/变体交叉冲突和并发创建均有覆盖；已用业务编码不变。修复任务P1-26.a/b；P1-03.b由已完成重新标为待验收，原通过证据保留。

### R05 / P2：重置密码可以保存登录接口必定拒绝的密码

- 证据：[resetPwd](../../erp-front/ruoyi-admin/src/main/java/com/ruoyi/web/controller/system/SysUserController.java)直接加密，没有服务端密码长度校验；[登录前置检查](../../erp-front/ruoyi-framework/src/main/java/com/ruoyi/framework/web/service/SysLoginService.java)使用[UserConstants](../../erp-front/ruoyi-common/src/main/java/com/ruoyi/common/constant/UserConstants.java)的5～20位范围。自助改密码入口也需同样审查。
- 实际复现：管理员将临时账号密码设为1字符，重置接口code=200，数据库确实保存了匹配该密码的哈希；带有效测试验证码用该密码登录得到code=500，因为在密码认证前被长度校验拒绝。
- 影响：前端校验被直接HTTP绕过，接口显示成功却造成不可用凭据；不能靠登录端拒绝代替写入端一致校验。
- 建议：新增/导入/管理员重置/自助修改与登录使用一致的服务端密码策略，先校验再持久化，不在本次审查发明新的复杂度规则。
- 关闭条件：非法值不写库；合法边界可登录；异常不得泄漏密码，且与R01会话撤销规则一致。修复任务P0-33。

### R06 / P2：供应商和类型表单未落实未保存退出保护

- 证据：[供应商页面](../../erp-back/src/views/erp/supplier/index.vue)和[类型页面](../../erp-back/src/views/erp/product-type/index.vue)的closeEdit直接设置editOpen=false，未做脏数据确认，也没有路由离开保护；对应新增动作重新初始化表单。作为对照，[汇率页面](../../erp-back/src/views/erp/exchange-rate/index.vue)已实现discardChanges和onBeforeRouteLeave。
- 静态确认：输入资料后取消/X/ESC会直接关闭，路由切换也没有本模块保护；重新新增会替换原输入，与需求第11章不一致。已有页面验收覆盖保存失败后保留输入，但未覆盖这两页主动离开时的确认。此次未重新进行浏览器操作，不将静态检查描述成新一轮UI验收。
- 建议：复用汇率页面既有模式，覆盖关闭、取消、路由离开和保存中离开，避免另建通用框架。
- 关闭条件：有修改时可取消离开并保留输入，无修改时不打扰，保存成功不误提示，保存中不能无提示离开。修复任务P1-27。

### R07 / P2：汇总任务被当作前置会造成实际确认业务与汇率快照互相等待

- 证据：[任务台账](../development/task-board.md)P2-10/P3-06/P7-04依赖汇总P1-18，P1-18.b又依赖“对应业务确认接口”。如果按前置完成后才开始执行，会等待采购/费用接口先完成快照，而接口本身又等整个汇率汇总完成。
- 影响：已经可用的P1-18.a基础服务不能转化为业务推进；容易反复开发预览而迟迟没有确认事务与快照持久化。阶段计划仍有“阶段0已开始，其余待开始”的旧描述，也与已有阶段1成果不一致，但不代表这些成果没有实际执行。
- 建议：业务命令前置写到P1-18.a；把相应快照持久化、原币/汇率/人民币金额及历史不回算列为该业务命令的共同交付与验收条件，P1-18.b只汇总核对各业务接入结果。修正其他汇总节点依赖和阶段描述，不改已确认财务规则。
- 关闭条件：关键执行路径不存在“父汇总等子任务、子任务再等父汇总”的等待环，每条确认事务有明确快照验收。修复任务P0-34。

| 类型`T-1`的第1个主SKU | `T-1-1` |
| 类型`T`的第1个主SKU | `T-1` |
| 上一主SKU的第1个变体 | `T-1-1`，与第一行冲突 |

唯一键正确拒绝重复，事务也会回滚；但重试会继续申请同一编码。两类型都已领号，受已用类型不可改码约束，当前界面无法恢复。不能放开唯一键、删除库存、改旧SKU或靠跳号碰运气解决。

优先建议正式类型码只允许字母与数字，把连字符保留为SKU层级分隔符，保持`类型码-主序号-变体序号`规则。主SKU仅一个分隔符、变体两个，能从规则上排除上述交叉；大小写仍遵循现有唯一比较规则。当前没有正式历史业务迁移要求，实施前仍须检查已分配记录，不自动把测试样例当正式资料。

若类型码必须含连字符，备选是在类型新增/改码时双向禁止“另一个类型码+正整数后缀”的重叠，按完整分段判断，并在事务内串行控制并发创建。该方案保留更多格式，但解释、实现和测试成本较高；不能只检查当时已有SKU，因为未来分配同样可能冲突。两种方案均涉及业务输入限制，P1-26.a待用户确认后实施。

### 汇率任务为何互等、如何拆解

原依赖：P2-10采购确认、P3-06收货成本、P7-04费用确认等待整个P1-18；P1-18包含b业务快照接入，而b又等业务确认接口。如果机械要求前置全部完成，就形成“业务确认→汇率汇总→业务快照→业务确认”的等待环。
